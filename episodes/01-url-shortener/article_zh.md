# URL Shortener：看似简单，实则不然

很多人觉得 URL Shortener 就是系统设计面试里的 "Hello World"。哈希一下 URL，存个映射，查到了就重定向——搞定了？远不止如此。Bitly 每月处理 6 亿次点击，TinyURL 每天处理数百万条 URL。深入一看，你其实在设计一个全球分布式、读密集型、带分析能力的系统，而且要求毫秒级响应。

## 为什么比想象中难

核心挑战在于**流量模式**。每缩短一条 URL，它可能会被点击 100 次。这意味着你要构建一个 99% 都是读的系统——但每天仍然要处理数百万次写入。再加上分析（按国家、设备、时间统计点击量）、防滥用和全球低延迟要求，你的 "简单" 项目瞬间变成了一个真正的工程挑战。

**规模速算：** 每日 1 亿条 URL 缩短 × 每条 100 次点击 = 每天 100 亿次重定向。相当于约 115,000 次读/秒和 1,200 次写/秒。存储 5 年？仅 URL 映射就约 90TB。

## 编码问题：如何生成短码

这是大多数候选人卡壳的地方。你的选项如下：

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **MD5/SHA + 截断** | 简单 | 碰撞不可预测，除了重试没有修复手段 | ❌ 避免 |
| **自增计数器** | 无碰撞，简单 | 可预测（爬虫风险），单点故障 | ⚠️ 单独使用有风险 |
| **Base62 + 计数器** | 紧凑，无碰撞 | 不做混淆则仍可预测 | ✅ 配合随机化使用 |
| **Snowflake 式 ID** | 唯一、分布式、不可预测 | 更复杂，码更长 | ✅ 大规模最佳选择 |

**Instagram 的方案**很优雅：将时间戳、机器 ID 和序列号组合，然后对整体做 Base62 编码。你无需单点协调就能获得唯一性，而且码不容易被预测到可以批量爬取。

> **关键洞察：** 哈希是个陷阱。在大规模下你无法高效检测或解决碰撞。基于计数器加分布式协调（如 Snowflake ID）的方案才是生产系统实际使用的方式。

## 面试框架

当你遇到这个题时，按这个路径走：

1. **功能需求** — 缩短 URL、重定向（301 还是 302？）、自定义别名、过期机制、分析
2. **规模估算** — 写 QPS、读 QPS、N 年的存储量、带宽
3. **高层架构** — 负载均衡 → Web 服务器 → 编码服务 → 数据库 + 缓存
4. **深入编码方案** — 如何无碰撞地生成短码
5. **缓存策略** — 100:1 的读比率要求激进缓存
6. **扩展** — 分析、限流、地理分布

301 vs 302 重定向的选择比你想的重要：301（永久）对 SEO 更好，但浏览器会缓存，导致分析数据不准。302（临时）确保每次点击都到达你的服务器——对精确追踪至关重要。

## 缓存：你最重要的决策

100:1 的读写比意味着你的缓存层可以说比数据库选型更重要。模式很直接：

**读路径：** 查缓存 → 命中？直接重定向。未命中？查 DB → 填充缓存 → 重定向。

**缓存什么：** 热度 top 20% 的 URL 会覆盖 80%+ 的流量。使用带 TTL 的 LRU 淘汰策略。几百 GB 的 Redis 就能处理数十亿条活跃映射。

**缓存失效：** 对 URL Shortener 来说基本不是问题——映射几乎不变。过期的 URL 自然被淘汰。这是少数缓存很简单的系统之一，因为数据本质上是不可变的。

## 数据库设计：SQL vs NoSQL

对于 URL 映射本身（short_code → long_url），你需要：
- 按 short_code 快速点查（重定向热路径）
- 创建新 URL 时的快速写入
- 水平扩展到数十亿行

**NoSQL（DynamoDB、Cassandra）** 是天然之选：主要访问模式就是键值查询，按 short_code 分片可以均匀分配负载。不需要 join。

**SQL（MySQL、PostgreSQL）** 在适当索引和分片下也可以工作，尤其当你需要 ACID 保证来做去重或自定义别名预留时。

**分片策略：** 对 short_code 做哈希来确定分片。如果使用 Snowflake 式 ID，码本身已经是伪随机的，自然获得均匀分布。

## 真实案例

**Bitly** 从单台 MySQL 实例演进到分布式架构。他们的关键洞察：将写路径（URL 创建）和读路径（重定向）完全分离。写入到主库；读取由副本和缓存提供服务。

**TinyURL** 保持简单——一个专注的架构证明了你并不总需要微服务。他们的成功表明，一个调优良好的单体配合优秀的缓存可以处理巨大的规模。

**Instagram 的 ID 生成** 在无需协调的情况下解决了分布式唯一性问题：每个分片使用（时间戳、shard_id、序列号）生成自己的 ID。这个模式直接适用于 URL Shortener 的短码生成。

## 核心要点

1. **这是一个读密集系统** — 从一开始就为 100:1 的比率设计。激进缓存。
2. **不要用哈希来生成短码** — 使用基于计数器或 Snowflake 式的分布式 ID 生成
3. **301 vs 302 是产品决策** — 分析需求 vs SEO 收益
4. **分离读写路径** — 它们有完全不同的规模特征
5. **缓存是你最大的杠杆** — 几百 GB 的 Redis 就能消除大部分数据库负载
6. **按 short_code 分片** — 均匀分布、快速查询、水平扩展
